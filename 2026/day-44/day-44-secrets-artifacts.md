# Task 1 — GitHub Secrets

## Objective

Store sensitive information securely and use it inside a GitHub Actions workflow without exposing the actual value in CI logs.

### Secret Created

```text
MY_SECRET_MESSAGE
```

### Workflow Concept

The secret was accessed using:

```yaml
${{ secrets.MY_SECRET_MESSAGE }}
```

It was passed to the workflow as an environment variable instead of printing the secret directly.

### Verification

The workflow checked whether the secret was available:

```text
The secret is set: true
```

The actual secret value was never printed.

## Why Secrets Should Never Be Printed

CI logs can be viewed by people with access to the repository or workflow.

Accidentally printing credentials, tokens, passwords, or API keys can expose sensitive infrastructure and services.

### Real Organizational Value

GitHub Secrets help organizations:

- Protect credentials
- Reduce accidental secret exposure
- Secure automated deployments
- Separate sensitive configuration from source code
- Improve security practices in CI/CD

# Task 2 — Secrets as Environment Variables

## Objective

Use a secret through an environment variable without hardcoding the sensitive value inside the workflow.

### Example

```yaml
env:
  MY_MESSAGE: ${{ secrets.MY_SECRET_MESSAGE }}
```

The workflow used the environment variable without displaying its actual value.

### Verification

```text
Secret received by the environment.
Secret length: 20
```

Only the length was displayed, not the secret itself.

## Docker Secrets

The following repository secrets were also created for future Docker CI/CD work:

```text
DOCKER_USERNAME
DOCKER_TOKEN
```

These credentials will be used later for authenticating with Docker Hub.

### Real Organizational Value

Environment variables and secrets allow teams to use the same pipeline across different environments while keeping sensitive values outside the source code.

# Task 3 — Upload Artifacts

## Objective

Generate a file during a workflow and preserve it after the workflow finishes.

A test report was generated:

```text
test-report.txt
```

Example content:

```text
Day 44 Test Report
Tests completed successfully.
Status: PASS
```

The workflow uploaded the file using:

```yaml
uses: actions/upload-artifact@v4
```

### Verification

The workflow completed successfully and the artifact was available from the GitHub Actions run.

## What Are Artifacts?

Artifacts are files produced by a workflow that need to be stored or shared after a job finishes.

Examples:

- Test reports
- Build outputs
- Logs
- Application packages
- Binaries
- Coverage reports

### Real Organizational Value

Artifacts help teams:

- Preserve important build outputs
- Investigate failed builds
- Share files between pipeline stages
- Keep test reports for later review
- Support deployment workflows

# Task 4 — Download Artifacts Between Jobs

## Objective

Create two jobs where the second job receives a file produced by the first job.

### Pipeline

```text
Job 1
Generate File
     |
     v
Upload Artifact
     |
     v
Job 2
Download Artifact
     |
     v
Read File
```

### Job 1

Generated:

```text
job1-output.txt
```

and uploaded it as:

```text
job1-output
```

### Job 2

The second job waited for Job 1 using:

```yaml
needs: generate
```

Then it downloaded the artifact using:

```yaml
uses: actions/download-artifact@v4
```

### Verification

The second job successfully printed:

```text
Hello from Job 1
This file was generated by the first job.
```

## Real-World Use

Artifacts between jobs are useful in multi-stage pipelines.

For example:

```text
Build
  |
  v
Test
  |
  v
Package
  |
  v
Deploy
```

A build stage can create an application package, upload it as an artifact, and a later deployment stage can download and deploy that exact output.

### Real Organizational Value

This helps teams:

- Connect multiple pipeline stages
- Avoid rebuilding the same output
- Keep build and deployment processes consistent
- Improve traceability
- Reduce unnecessary work

# Task 5 — Run Real Tests in CI

## Objective

Run an actual Python script in GitHub Actions and verify that CI correctly detects both successful and failing tests.

### Python Test

The test script contained a simple addition test:

```python
def add(a, b):
    return a + b


def test_add():
    assert add(2, 3) == 5
```

The test was first executed locally and passed.

```text
All tests passed!
```

### CI Workflow

The GitHub Actions workflow:

1. Checked out the repository
2. Set up Python
3. Ran the Python test script

### Successful CI Run

```text
Checkout repository     PASS
Setup Python             PASS
Run Python tests         PASS
```

The pipeline completed successfully.

---

## Intentionally Breaking the Test

The test was intentionally changed from:

```python
assert add(2, 3) == 5
```

to:

```python
assert add(2, 3) == 10
```

The workflow then failed.

```text
Intentionally break CI test
FAIL
```

This demonstrated that CI can automatically detect broken code.

---

## Fixing the Test

The assertion was changed back to:

```python
assert add(2, 3) == 5
```

After pushing the fix, GitHub Actions ran again and passed.

```text
fix failing CI Test
PASS
```

### CI Feedback Loop

```text
Code Change
    |
    v
CI Runs Tests
    |
    +---- PASS ----> Continue Pipeline
    |
    +---- FAIL ----> Stop / Fix Code
```

### Real Organizational Value

Automated tests in CI help organizations:

- Catch bugs early
- Prevent broken code from moving forward
- Maintain software quality
- Reduce manual testing
- Increase confidence in releases
- Create fast feedback for developers

# Task 6 — Dependency Caching

## Objective

Use caching to avoid repeatedly downloading the same dependencies.

A Python dependency file was created:

```text
requirements.txt
```

with:

```text
pytest
```

The workflow used:

```yaml
uses: actions/setup-python@v5
with:
  python-version: "3.12"
  cache: "pip"
```

## First Run

During the first run:

```text
pip cache is not found
```

This was a cache miss.

The workflow downloaded and installed the dependencies.

After installation, GitHub Actions saved the cache:

```text
Cache saved with the key: ...
```

### Flow

```text
First Run
   |
   v
Cache Miss
   |
   v
Download Dependencies
   |
   v
Install Dependencies
   |
   v
Save Cache
```

## Second Run

The workflow was run again to verify that the previously created cache could be reused.

### Why Caching Matters

Caching can reduce repeated dependency downloads and make CI workflows more efficient.

### Real Organizational Value

Caching helps organizations:

- Reduce build time
- Reduce unnecessary network downloads
- Improve CI efficiency
- Save runner resources
- Make frequent pipeline runs faster
- Reduce infrastructure costs

---

# Artifacts vs Cache

Understanding the difference between artifacts and caches is important.

| Feature | Artifacts | Cache |
|---|---|---|
| Main purpose | Store workflow outputs | Speed up future workflows |
| Example | Test report | Python packages |
| Lifetime/use | Preserve and share files | Reuse reusable dependency data |
| Typical use | Build outputs, logs, reports | npm, pip, Maven dependencies |

### Easy Way to Remember

```text
Artifact = Keep my output

Cache = Make my next run faster
```
